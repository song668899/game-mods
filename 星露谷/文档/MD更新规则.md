# 📋 MD 文档更新规则

> **给所有参与本项目的人 / AI：更新任何 MD 文件前，先读完这一页。**
> 目的：让文档**好查、不重复、不误导**。
> 制定日期：2026-10-01

---

## 一、先决定：这条记录该写进哪个文件？

**按"环境"和"性质"两个维度判断，不要随手往最近的文档里塞。**

| 你做的事 | 写进 |
|---|---|
| 改 **Steam 环境**（`D:\Apps\Steam\...`）的 MOD | `Steam环境-MOD记录.md` |
| 玩/配 **整合包环境**（`D:\星露谷MOD\游戏`） | `整合包环境-使用记录.md` |
| 总结出**可复用的方法、机制、踩坑** | `技术笔记-汉化与DLL修改.md` |
| 用 dnSpy 的具体操作步骤 | `dnSpy翻译指南.md` |
| 环境概览、文档导航变了 | `README.md` |

### 关键区分：「做过的事」vs「学到的方法」

| | 例子 | 归属 |
|---|---|---|
| **做过的事**（一次性） | "给 Frontier Farm 加了 22 个 i18n 键" | Steam 记录 |
| **学到的方法**（可复用） | "CP 的键名约定是 `config.<字段>.name`" | **技术笔记** |

**同一次工作往往两样都有 → 拆开写。**
记录里写"做了什么"，方法写进技术笔记，记录里留一行指针。

> 例：改 MailServicesMod 时
> - Steam 记录：「替换了 52 个串，67072 字节不变」
> - 技术笔记：「DLL 等长替换必须长串优先，因为 `Gift Service` 是 `Gift Service:` 的子串」

## 二、记录格式（统一模板）

### 2.1 章节标题：日期开头，`##` 级

```markdown
## 2026-10-01 做了什么（简述）
```

同一天多场工作，用场次后缀：

```markdown
## 2026-10-01 下半场：GMCM 英文清理
## 2026-10-01 第三场：PolyamorySweet 汉化
```

**禁止**用 `#` 一级标题（那是文档标题专用），也**禁止**不带日期的标题。

### 2.2 章节内容：四要素

每次工作至少写清这四项：

```markdown
## 2026-10-01 修复 XXX 显示英文

**问题**：什么现象、谁发现的、触发条件

**根因**：为什么会这样（要写证据，不要猜）

**处理**：具体改了什么文件、什么方式

**验证**：怎么确认改对了（日志/哈希/字节数）

**备份**：改动前的文件在哪（没备份就写「未备份」）

**⚠️ 注意**：将来会踩的坑（如"MOD 更新会覆盖汉化"）
```

### 2.3 必须写进记录的内容

- ✅ **文件路径**（完整或相对仓库根目录）
- ✅ **关键数字**（字节数、键数、组件数）——便于将来核对
- ✅ **证据来源**（SMAPI 日志第几行、哈希值、字节数比较）
- ✅ **备份位置**（回滚用）
- ✅ **未做的事**（如果本来该做但没做，写清楚，别让人以为做完了）

### 2.4 不要写进记录的

- ❌ 想法过程、试错细节（除非是"踩坑"要写进技术笔记）
- ❌ 大段代码（放技术笔记或单独文件）
- ❌ 与本次工作无关的背景介绍

## 三、写「踩坑」的规则

**踩坑一律写进 `技术笔记-汉化与DLL修改.md`，不要散落在各记录里。**

每条坑必须包含：

```markdown
### N. 一句话结论（用**粗体**标出关键）

现象/报错原文（如果有）

**原因**：为什么

**正确做法**：具体怎么做，最好给代码片段

> 实例：在哪次工作中遇到的（便于溯源）
```

**判断标准**：如果这条经验**下次还会用到**，才写进技术笔记；一次性的问题只写进环境记录。

## 四、更新文档时的硬性要求

### 1. 改前先读

不要凭记忆改。**先读现有文档**，看这件事是否已记录过：
- 已记录 → 补充/修正，别新开一段
- 未记录 → 按模板新开一段

### 2. 同步更新三处

改了内容，别忘了：

| 位置 | 更新什么 |
|---|---|
| 文首 `> 最后更新：YYYY-MM-DD` | 改成今天 |
| 文档内的**目录**（如果有） | 加上新章节 |
| `README.md` 的「当前状态速查」 | 如果规模/状态变了 |

### 3. 保持链接有效

写 `[文字](文件名.md)` 前**确认文件存在**。重命名文件时，用搜索找出所有引用并同步改。

### 4. 不要复制粘贴

同一段内容**只在一处写全**，别处留指针：
```markdown
> 详见 [技术笔记-汉化与DLL修改.md](技术笔记-汉化与DLL修改.md) 第 N 节
```

### 5. 数字要准确

写"59 mods + 34 packs"这类数字前，**去核实**（看 SMAPI 日志），别照抄旧文档——环境是会变的。

## 五、新增文档的命名规则

```
<环境>-<用途>.md          例：Steam环境-MOD记录.md、整合包环境-使用记录.md
<性质>-<主题>.md          例：技术笔记-汉化与DLL修改.md
归档-<日期>-<主题>.md      例：归档-2026-09-05对话记录.md
```

**新增文档后，必须在 `README.md` 的「文档地图」里登记。**

### 存放位置

**所有 MD 放 `D:\星露谷MOD\文档\`，只有 `README.md` 留在仓库顶层。**

新增文档时：

1. 存进 `文档\`
2. 在 `README.md` 的「文档地图」表格里加一行
3. 文档**之间**互链用同目录相对路径（例：`技术笔记-汉化与DLL修改.md`）
4. 从**顶层的 `README.md`** 链过去要带目录前缀（例：`文档/技术笔记-汉化与DLL修改.md`）
5. 改完**校验链接有效性**（脚本见下）

```python
# 链接校验
import os, re
def check(path, base):
    t = open(path, encoding='utf-8').read()
    return [h for _, h in re.findall(r'\[([^\]]+)\]\(([^)]+)\)', t)
            if not h.startswith(('http', '#')) and '://' not in h
            and not os.path.exists(os.path.normpath(os.path.join(base, h)))]
```

## 六、自查清单（提交前过一遍）

```
□ 写进正确的文件了吗？（环境记录 vs 技术笔记）
□ 章节标题带日期、是 ## 级吗？
□ 四要素（问题/根因/处理/验证）齐了吗？
□ 关键数字核实过吗？（不是照抄旧文档）
□ 备份位置写了吗？
□ 文首「最后更新」改了吗？
□ README 的文档地图/状态需要同步吗？
□ 链接都有效吗？
□ 有没有和别处重复的内容？（该改成指针）
```

## 七、反例（这些做法会让文档烂掉）

| ❌ 错误做法 | 后果 |
|---|---|
| 把方法论写在环境记录里 | 下次改别的 MOD 时找不到，重复踩坑 |
| 只写"修好了"，不写怎么修的 | 无法回溯，出问题无法回滚 |
| 章节不带日期 | 不知道是新记录还是旧内容 |
| 同一内容复制到多个文档 | 改一处忘一处，文档互相矛盾 |
| 照抄旧文档的数字 | 环境变了也不知道 |
| 改了内容不更新「最后更新」 | 无法判断文档是否过时 |
| 踩坑只在对话里说，不写文档 | 会话结束就丢了 |

---

**最后一条：文档是给"未来的自己"和"下一个 AI"看的。**
你这次踩的坑，下次可能换个人再踩一遍——写下来才有价值。
